# Decisions

Final choices for the open items in [AGENT_PLAN.md § 10](AGENT_PLAN.md#10-decisions-recommended-defaults). Until an item appears here, use the default listed in the plan.

| # | Decision | Choice | Decided by | Date |
|---|---|---|---|---|
| D1 | Browser offline | **The browser is online-only in v1.** `LekhaBook.Web` calls `LekhaBook.Api` directly. Offline use is through the MAUI app (Android, iOS, Windows). A browser PWA with local storage and the same sync engine can come in a later version. Keep `LekhaBook.UI` behind interfaces so that stays possible. | User | 2026-11-23 |
| D2 | Date system | **Store AD; display BS by default, AD selectable per company.** BS date picker; lakh number grouping (`10,00,000`); currency `Rs.` Confirmed by discovery: Karobar users work in BS. | User (scope approval) | 2026-11-23 |
| D3 | Product branding | **Lekha Books** is the visible product name. Original open-ledger/checkmark artwork uses the existing indigo and teal palette. The shared UI owns the master PNG, and the native icon and splash reference that same file. Technical project names, namespaces and application ID stay `LekhaBook`. | User requested logos and project integration; agent selected the design | 2026-11-24 |
| D7 | Income/expense categories | **Categories are `Account` rows** of type Income or Expense, seeded per company. No separate category tables; transactions carry only From/To account ids (no `PartyId`/`CategoryId`), so no two columns can disagree. `PartyCategory` stays a plain lookup. | Agent (phase 3, advisor-reviewed) | 2026-11-24 |
| D8 | Opening balances | **Stored on the account** (amount, side, as-of date), matching the Add Party / Add Account forms. No opening transaction; opening equity is computed. Because they are money, concurrent edits to opening fields go to conflict review during sync. | Agent (phase 3, advisor-reviewed) | 2026-11-24 |
| D9 | Shared EF model | New **`LekhaBook.Data`** project holds the EF model both databases share (`LekhaBookDbContext`, depends on Domain only). `Data.Sqlite` adds device-only tables (Outbox, LocalAttachmentFiles, SyncCheckpoints); `Data.Postgres` adds `CompanySyncStates`. Money stays `decimal` on SQLite too (EF Core 10 translates `Sum`/compare with `ef_*` functions); timestamps are UTC `DateTime`; enums are stored as text. | Agent (phase 3) | 2026-11-24 |
| D5 | Login method | **Email + password** via ASP.NET Core Identity API endpoints (`/api/auth/*`). Phone OTP and Google sign-in later; PIN/biometric device unlock later. | Agent (phase 4, plan default) | 2026-11-24 |
| D10 | Auth tokens and storage | Identity's **opaque bearer access token + refresh token** (not JWT), issued by `MapIdentityApi`. Identity tables live in their own `AuthDbContext` (same PostgreSQL database, separate migrations history `__EFMigrationsHistory_Auth`). Company roles are **not** Identity roles. Data-protection keys must be persisted in production (D4 deployment), or tokens break on restart. | Agent (phase 4, advisor-reviewed) | 2026-11-24 |
| D11 | Membership storage | `CompanyMember` and `Invitation` are **server-only** (PostgreSQL), not synced: the server is the only writer and staff details shouldn't be copied to every device. Devices cache their own `/api/me` response for offline permission checks. Permissions are stable string keys; a custom set replaces the role template; the Owner can't be customised, changed or removed, nobody can grant what they don't hold, and nobody can manage someone whose access exceeds theirs. **Known v1 gaps:** email confirmation is off and there's no email sender yet, so an invite's email check only matches an *unconfirmed* address (the single-use, hashed token is the real secret; on the web it travels in URLs such as `/invite?token=` and sign-in return URLs, so it can appear in browser history and server logs, which is acceptable because it is single use and expires in 7 days) and `forgotPassword` can't deliver a reset link. Both close when email sending is added. | Agent (phase 4, advisor-reviewed) | 2026-11-24 |
| D12 | Company "today" | `Company.TimeZoneId` (default `Asia/Kathmandu`, UTC+5:45) defines the company's date for Lock Transaction Date and same-day edits; computed from the server clock via `TimeProvider`, never the device clock. | Agent (phase 4) | 2026-11-24 |
| D13 | Client sessions | One shared sign-in UI and `SessionService` (LekhaBook.Client); each host only stores tokens. **MAUI:** tokens in `SecureStorage`, one session per app (singletons); offline start keeps the user signed in with the cached `/api/me`; only a rejected refresh signs out. **Web:** the refresh token lives in an HttpOnly, SameSite=Lax auth cookie (14 days); App.razor reads it during the HTTP request and hands it to the circuit as an encrypted component parameter; the circuit refreshes for an access token and keeps tokens in memory; session/API services are **Scoped (one per circuit)**. Interactive components can't set cookies, so sign-in uses a one-time ticket (32 random bytes, 60 s, single use, **bound to a per-browser HttpOnly cookie** against login CSRF) and a full-page redirect; sign-out uses a circuit-issued nonce. Prerendering is off for the web root. **Limits:** Identity refresh tokens aren't revoked server-side, so signing out ends the session on that device/browser only; "sign out everywhere" (security-stamp update) comes later. The cookie carries the refresh token issued at sign-in, so **web users sign in again after 14 days** (no sliding renewal). The ticket cache is in-memory (single web server, D4). The web host's auth cookie, `ProtectedLocalStorage` and encrypted component parameters all depend on ASP.NET data-protection keys, which must be persisted in production. Revocation reaches an open session on its next `/api/me` (page reload, or after a 403); open sessions aren't pushed a notice. | Agent (phase 4b, advisor-reviewed) | 2026-11-24 |
| — | v1 scope | **Approved** as in `discovery/00-summary.md` § 4. AGENT_PLAN §§ 4.2, 5.1, 5.2, 5.4, 8.3 and 8.4 updated to match: Cheque/Wallet accounts, Karobar-style transaction names, per-module permission matrix with role templates (Owner, Partner, Manager, Accountant, Entry Person), Manual/Auto numbering with prefixes, and Karobar-compatible shortcuts. Entry Person sees balances but can't change settings (unlike Karobar). | User | 2026-11-23 |
