| D13 | Client sessions | One shared sign-in UI and `SessionService` (LekhaBook.Client); each host only stores tokens. **MAUI:** tokens in `SecureStorage`, one session per app (singletons); offline start keeps the user signed in with the cached `/api/me`; only a rejected refresh signs out. **Web:** the refresh token lives in an HttpOnly, SameSite=Lax auth cookie (14 days); App.razor reads it during the HTTP request and hands it to the circuit as an encrypted component parameter; the circuit refreshes for an access token and keeps tokens in memory; session/API services are **Scoped (one per circuit)**. Interactive components can't set cookies, so sign-in uses a one-time ticket (32 random bytes, 60 s, single use, **bound to a per-browser HttpOnly cookie** against login CSRF) and a full-page redirect; sign-out uses a circuit-issued nonce. The web host's auth cookie, `ProtectedLocalStorage` and encrypted component parameters all depend on ASP.NET data-protection keys, which must be persisted in production. | D14 | Masters data path until sync | **Phases 5–7: both hosts read and write parties and money accounts through the API** (`IDataService` → `ApiDataService` in LekhaBook.Client), so the MAUI app needs a connection for these screens until phase 8. Screens show a clear "needs a connection" state instead of failing. To make the phase 8 switch to SQLite + outbox a DI change only: the **client generates the id** (UUIDv7) and a repeated create with the same id returns the existing row (no duplicates on retry); the server stamps `Version` (per-company counter row, locked inside the write transaction, one version per row), `CreatedAtUtc`/`UpdatedAtUtc` and `CreatedBy`/`UpdatedBy`, and writes an `AuditLog` row for every edit and delete. Party permissions follow the party type (Customer → `parties.customers.*`, Supplier → `parties.suppliers.*`; changing the type needs edit on the old type and create on the new one). An account used by any transaction, or a system account, can't be deleted. **Add Account also offers Cash** (petty cash, v1 scope), not only Bank and Wallet as in Karobar. Opening "as of" dates are AD until BS dates land (phase 10); users with Lock Transaction Date can only date an opening balance today. | Implementation (phase 5) | 2026-11-24 |
| D15 | Transactions data path & voiding | **Phase 6: transactions flow through the API like masters (D14).** One row moves value From (credited) one account To (debited) another; there is no leg table. The client generates the UUIDv7 id; a repeated create returns the saved row. **"Delete" is void:** the row is kept with `Status = Void`, and balances and statements skip it. An entry's type can't be edited. Every create, edit and void writes an `AuditLog` row. | D17 | Sync API | **Push** (`POST /api/companies/{companyId}/sync/push`, at most 200 items) writes through the same code as online saves, so posting rules, entry rules, permissions and audit apply. Attachment rows are never synced up: only the upload endpoint creates them and names the stored file. Items are applied in order and saved one at a time. A refused item is a result inside a 200; only the membership check returns 403, because devices wipe a company on 403. An update or void carries the `BaseVersion` it was made from: a change already applied is a success, otherwise a version mismatch is a conflict. **Pull** (`GET …/sync/pull?since=&take=`) gives every member all rows (plan § 4.2), one page across tables in version order; the returned cursor never passes a row that wasn't sent. **Not decided or built:** voucher numbers are not assigned on push; the device does not yet queue changes; a device editing its own unsynced entry would get a conflict unless its outbox merges the two changes; "same day" and Lock Transaction Date use the day the change reaches the server, so a lock-dated user's offline entry from yesterday is refused. | Implementation (phase 8) | 2026-11-26 |
