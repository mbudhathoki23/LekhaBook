# Decisions

Final choices for the open items in [AGENT_PLAN.md § 10](AGENT_PLAN.md#10-decisions-recommended-defaults). Until an item appears here, use the default listed in the plan.

| # | Decision | Choice | Decided by | Date |
|---|---|---|---|---|
| D1 | Browser offline | **The browser is online-only in v1.** `LekhaBook.Web` calls `LekhaBook.Api` directly. Offline use is through the MAUI app (Android, iOS, Windows). A browser PWA with local storage and the same sync engine can come in a later version. Keep `LekhaBook.UI` behind interfaces so that stays possible. | User | 2026-11-23 |
| D2 | Date system | **Store AD; display BS by default, AD selectable per company.** BS date picker; lakh number grouping (`10,00,000`); currency `Rs.` Confirmed by discovery: Karobar users work in BS. | User (scope approval) | 2026-11-23 |
| D3 | Product branding | **Lekha Books** is the visible product name. Original open-ledger/checkmark artwork uses the existing indigo and teal palette. The shared UI owns the master PNG, and the native icon and splash reference that same file. Technical project names, namespaces and application ID stay `LekhaBook`. | User requested logos and project integration; design chosen during implementation | 2026-11-24 |
| D7 | Income/expense categories | **Categories are `Account` rows** of type Income or Expense, seeded per company. No separate category tables; transactions carry only From/To account ids (no `PartyId`/`CategoryId`), so no two columns can disagree. `PartyCategory` stays a plain lookup. | Implementation (phase 3) | 2026-11-24 |
| D8 | Opening balances | **Stored on the account** (amount, side, as-of date), matching the Add Party / Add Account forms. No opening transaction; opening equity is computed. Because they are money, concurrent edits to opening fields go to conflict review during sync. | Implementation (phase 3) | 2026-11-24 |
| D9 | Shared EF model | New **`LekhaBook.Data`** project holds the EF model both databases share (`LekhaBookDbContext`, depends on Domain only). `Data.Sqlite` adds device-only tables (Outbox, LocalAttachmentFiles, SyncCheckpoints); `Data.Postgres` adds `CompanySyncStates`. Money stays `decimal` on SQLite too (EF Core 10 translates `Sum`/compare with `ef_*` functions); timestamps are UTC `DateTime`; enums are stored as text. | Implementation (phase 3) | 2026-11-24 |
| D5 | Login method | **Email + password** via ASP.NET Core Identity API endpoints (`/api/auth/*`). Phone OTP and Google sign-in later; PIN/biometric device unlock later. | Plan default (phase 4) | 2026-11-24 |
| D10 | Auth tokens and storage | Identity's **opaque bearer access token + refresh token** (not JWT), issued by `MapIdentityApi`. Identity tables live in their own `AuthDbContext` (same PostgreSQL database, separate migrations history `__EFMigrationsHistory_Auth`). Company roles are **not** Identity roles. Data-protection keys must be persisted in production (D4 deployment), or tokens break on restart. | Implementation (phase 4) | 2026-11-24 |
| D11 | Membership storage | `CompanyMember` and `Invitation` are **server-only** (PostgreSQL), not synced: the server is the only writer and staff details shouldn't be copied to every device. Devices cache their own `/api/me` response for offline permission checks. Permissions are stable string keys; a custom set replaces the role template; the Owner can't be customised, changed or removed, nobody can grant what they don't hold, and nobody can manage someone whose access exceeds theirs. **Known v1 gaps:** email confirmation is off and there's no email sender yet, so an invite's email check only matches an *unconfirmed* address (the single-use, hashed token is the real secret; on the web it travels in URLs such as `/invite?token=` and sign-in return URLs, so it can appear in browser history and server logs, which is acceptable because it is single use and expires in 7 days) and `forgotPassword` can't deliver a reset link. Both close when email sending is added. | Implementation (phase 4) | 2026-11-24 |
| D12 | Company "today" | `Company.TimeZoneId` (default `Asia/Kathmandu`, UTC+5:45) defines the company's date for Lock Transaction Date and same-day edits; computed from the server clock via `TimeProvider`, never the device clock. | Implementation (phase 4) | 2026-11-24 |
| D13 | Client sessions | One shared sign-in UI and `SessionService` (LekhaBook.Client); each host only stores tokens. **MAUI:** tokens in `SecureStorage`, one session per app (singletons); offline start keeps the user signed in with the cached `/api/me`; only a rejected refresh signs out. **Web:** the refresh token lives in an HttpOnly, SameSite=Lax auth cookie (14 days); App.razor reads it during the HTTP request and hands it to the circuit as an encrypted component parameter; the circuit refreshes for an access token and keeps tokens in memory; session/API services are **Scoped (one per circuit)**. Interactive components can't set cookies, so sign-in uses a one-time ticket (32 random bytes, 60 s, single use, **bound to a per-browser HttpOnly cookie** against login CSRF) and a full-page redirect; sign-out uses a circuit-issued nonce. Prerendering is off for the web root. **Limits:** Identity refresh tokens aren't revoked server-side, so signing out ends the session on that device/browser only; "sign out everywhere" (security-stamp update) comes later. The cookie carries the refresh token issued at sign-in, so **web users sign in again after 14 days** (no sliding renewal). The ticket cache is in-memory (single web server, D4). The web host's auth cookie, `ProtectedLocalStorage` and encrypted component parameters all depend on ASP.NET data-protection keys, which must be persisted in production. Revocation reaches an open session on its next `/api/me` (page reload, or after a 403); open sessions aren't pushed a notice. | Implementation (phase 4b) | 2026-11-24 |
| D14 | Masters data path until sync | **Phases 5–7: both hosts read and write parties and money accounts through the API** (`IDataService` → `ApiDataService` in LekhaBook.Client), so the MAUI app needs a connection for these screens until phase 8. The device database holds no company rows or seeded accounts until sync can pull them, and seeding locally would create a second Cash account with a different id. Screens show a clear "needs a connection" state instead of failing. To make the phase 8 switch to SQLite + outbox a DI change only: the **client generates the id** (UUIDv7) and a repeated create with the same id returns the existing row (no duplicates on retry); the server stamps `Version` (per-company counter row, locked inside the write transaction, one version per row), `CreatedAtUtc`/`UpdatedAtUtc` and `CreatedBy`/`UpdatedBy`, and writes an `AuditLog` row for every edit and delete. Party permissions follow the party type (Customer → `parties.customers.*`, Supplier → `parties.suppliers.*`; changing the type needs edit on the old type and create on the new one). An account used by any transaction, or a system account, can't be deleted. **Add Account also offers Cash** (petty cash, v1 scope), not only Bank and Wallet as in Karobar. Opening "as of" dates are AD until BS dates land (phase 10); users with Lock Transaction Date can only date an opening balance today. | Implementation (phase 5) | 2026-11-24 |
| D15 | Transactions data path & voiding | **Phase 6: transactions flow through the API like masters (D14).** One row moves value From (credited) one account To (debited) another; there is no leg table. The server applies `PostingRules` (account kinds, same company, two different accounts, 2 decimals) and `EntryRules` (permission per entry type, own entries only, same-day edits, Lock Transaction Date), loads accounts only from the route's company, and rejects future dates. There are no separate "transactions" permissions. The client generates the UUIDv7 id; a repeated create returns the saved row. **"Delete" is void:** the row is kept with `Status = Void`, and balances and statements skip it. An entry's type can't be edited. Every create, edit and void writes an `AuditLog` row. A null date on create means the company's today (D12). `VoucherNo` is the entry id, marked provisional and hidden in the UI, until voucher numbering is built (phase 8). | Implementation (phase 6) | 2026-11-26 |
| D16 | Attachment storage & upload path | **Phase 7 (partial): attachments upload through the API** (`POST /api/companies/{companyId}/attachments` multipart with a required `transactionId`; `GET …/attachments?transactionId=`; `GET …/attachments/{id}`). Adding one needs the right to edit that entry; reading needs the right to view it. The server checks the declared type (jpeg/png/webp/pdf) and size (max 5 MB). Files are stored under `attachments/<companyId>/` next to the API binaries, which is for development only. **Not built yet:** durable storage (D6), checking file contents, compression and the upload queue. Deleting, the limit of 5 and camera capture were added in D19. | Implementation (phase 7) | 2026-11-26 |
| D17 | Sync API | **Push** (`POST /api/companies/{companyId}/sync/push`, at most 200 items) writes through the same code as online saves, so posting rules, entry rules, permissions and audit apply. Items: `Transaction` Create/Update/Void and `PartyCategory` Create, with the client's id; anything else is refused. Attachment rows are never synced up: only the upload endpoint creates them and names the stored file. Items are applied in order and saved one at a time. A refused item is a result inside a 200; only the membership check returns 403, because devices wipe a company on 403. An update or void carries the `BaseVersion` it was made from: a change already applied is a success, otherwise a version mismatch is a conflict. **Pull** (`GET …/sync/pull?since=&take=`) gives every member all rows (plan § 4.2), one page across tables in version order; the returned cursor never passes a row that wasn't sent. **Not decided or built:** voucher numbers are not assigned on push; the device does not yet queue changes; a device editing its own unsynced entry would get a conflict unless its outbox merges the two changes; "same day" and Lock Transaction Date use the day the change reaches the server, so a lock-dated user's offline entry from yesterday is refused. | Implementation (phase 8) | 2026-11-26 |
| D18 | Localization (English and Nepali) | **Two languages in one shared resource set:** `LekhaBook.UI/Localization/SharedResource.resx` (English, the default) and `SharedResource.ne.resx` (Nepali, `ne`). Razor components write `@Loc["Key"]` (`IStringLocalizer<SharedResource>`). MudBlazor's own text (pager, date picker) goes through `ResxMudLocalizer`, and a key the app doesn't translate falls back to MudBlazor's English. The language is chosen in Settings and on the sign-in page (`LanguageSwitcher`, `ILanguageService`). **Web:** a culture cookie set by `/culture/set` and read by RequestLocalization; only that cookie chooses (not `?culture=` or the browser language, so English stays the default); a change reloads the page. **MAUI:** saved in Preferences and applied before the first screen; a change re-creates the layout. Amounts keep ASCII digits and lakh grouping; dates stay as D2 (BS display comes in phase 10). **Form checks** are translated: `MasterValidation` keeps the English wording (used by the server) and the forms pass the screen's wording as a `ValidationText`. **Limits:** server and API error messages are still English, because the client shows them as the server sends them. | User request, brought forward from phase 10 (AGENT_PLAN § 8.5) | 2026-11-26 |
| D19 | Voucher images, company logo and statements | **Voucher images:** an entry can carry up to 5 JPEG, PNG, WebP or PDF files, 5 MB each; the server enforces the limit and the declared type. Images show as thumbnails and open in a preview. Files are fetched through the API with the user's session, never as public links, and PDFs are fetched only when opened. A new entry can be saved with files, which upload once the entry is saved. Deleting a file needs edit rights on the entry and is a soft delete, so the file stays on disk. Phones get a "Take photo" input as well as the file picker. **Company logo:** one JPEG, PNG or WebP image, up to 2 MB. Any member can read it; only users with business-settings permission can set or remove it. It is stored next to the company's attachments. **Statements:** each line carries its cheque number and the files the user may view for that entry (the D16 view rule). The statement header shows the company logo and details and the party or account details, and "Print statement" uses the browser's print, so no PDF is generated. **Limits:** durable storage (D6), content checks, compression and the upload queue are still not built. | Implementation (phase 7) | 2026-11-26 |
| D20 | Nepali miti (BS) display and entry | **Builds D2; dates stay AD in the database, API and sync.** `LekhaBook.Domain/NepaliCalendar.cs` converts with a month-length table taken from the user's reference list (Shrawan 2075 to Ashad 2090, AD 2018-07-17 to 2033-07-15), tested day by day against that list. Each company chooses **BS (default) or AD** when it is created or in Settings (`PUT /api/companies/{id}/calendar`, business-settings permission); the choice travels in `CompanySummary`. BS companies see `yyyy/mm/dd` miti in lists, statements and staff dates, and enter dates through `DateField`: typed, or picked from a miti calendar. AD companies keep the standard date picker. A date outside the table is shown as AD and can't be typed as a miti. **Open:** BS year 2087 in the reference list has 367 days; check 2087 and 2088 against an official calendar before they are used. The table needs extending before Ashad 2090. Fiscal-year logic is not built. Supersedes the "AD until BS dates land" notes in D14 and D18. | User request, brought forward from phase 10 | 2026-11-26 |
| D21 | Screen names | **"Transactions" is shown as "Entry" and "Cash & Bank" as "Finance"** (Nepali: प्रविष्टि and वित्त), and screen text says "entry" rather than "transaction". Only displayed wording changes: code names, resource keys, routes (`/transactions`, `/accounts`), API paths, database tables and sync entity types keep their names. | User request | 2026-11-26 |
| D22 | Dashboard: money in and out, monthly, yearly and top parties | **Built from the posted entries the user can see, in one pure function** (`LekhaBook.Application/DashboardFlows.cs`, 7 tests), not a new server endpoint yet. **Money in** is payments received from parties and other income. **Money out** is payments made to parties and expenses. Transfers between accounts and balance adjustments are left out. **Monthly** is the last 12 months and **yearly** the last 5 fiscal years, in the company's calendar (Bikram Sambat months, or AD). A fiscal year starts in `FiscalYearStartMonth` of that calendar (Nepal: 4 = Shrawan). **Top 5 parties** are the most payments in and out in the current fiscal year, with each party's balance now. Shown to users with `reports.dashboard`. Colours: blue for money in and orange for money out; the amounts are always written beside the bars. **Limits:** the whole posted list loads on each visit, which is fine for a small business but not for years of data; dates outside the Bikram Sambat table (2018 to 2033 AD) are not placed; the figures aren't yet served by the plan's `reports/` endpoints, so the server checks the transactions view rather than `reports.dashboard`. Built before phases 6 and 8 are closed, at the user's request. | User request | 2026-11-26 |
| D23 | More languages and right-to-left | **Extends D18** with Bengali (`bn`), Arabic (`ar`, one Modern Standard Arabic text for the UAE, Saudi Arabia and Oman), Simplified Chinese (`zh`) and Japanese (`ja`), each in `SharedResource.{code}.resx`. **Arabic is right to left:** `MudRTLProvider` in both layouts, `dir` on the web page, logical CSS properties, mirrored back and calendar arrows, and amounts isolated so the sign, "Rs." and digits keep their order. **Formats do not follow the language** (`Languages.CultureFor`): Gregorian AD dates (no Hijri), "." decimals, Western digits and the D2 "Rs." lakh amounts. A test fails when any language is missing an English key. **Limits:** the translations have not been reviewed by native speakers; currency stays Rs. with 2 decimals (the Omani rial uses 3); server error messages stay English. | User request | 2026-11-26 |
